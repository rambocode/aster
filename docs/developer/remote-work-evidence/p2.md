   ### 根因一：显示桥的 `surface.subscribe` 被服务端按 `invalid_request` 拒绝

   - **是什么。** `SessionRuntime/src/surface_service.zig` 的 `checkGeometry` 拿客户端上报的原始 `ws_xpixel/ws_ypixel` 去比服务端会话里保存的像素尺寸。但会话只保存**按单元格量化后**的尺寸：`Session.resizeGeometry` 把几何交给 `Terminal.resizeGeometry`，后者只传 `Geometry.cellWidth() = pixel_width / columns` 与 `cellHeight() = pixel_height / rows`（整数除法，`geometry.zig` 明确写了「Division removes any partial trailing cell」），于是 VT 回读到的是 `cellWidth×columns`。只要客户端像素尺寸不是列数/行数的整数倍，`checkGeometry` 必然判成 `UnsupportedProjection`，`surface_service.respond` 把它统一映射成 `invalid_request`。
   - **为什么真实 App 必中、手工复现必不中。** 真实 Ghostty surface 的 PTY 会上报真实像素尺寸，几乎不可能正好是整数倍；而先前的手工重放是在普通终端里跑的，那些 PTY 的 `ws_xpixel/ws_ypixel` 为 0，`localGeometry()` 直接返回 0（表示不可用），比较分支根本不进入，所以「同样的 attach」重放成功。
   - **为什么单测没抓到。** 两处都恰好用了整除的数：`session.zig` 的 `"measured pixel geometry reaches both PTY and VT without guessed defaults"` 用 1000/100 与 600/30；`SessionRuntime/tests/terminal_attach.py` 的宿主 PTY 一直用 `struct.pack("HHHH", rows, columns, 0, 0)`，即像素尺寸恒为 0。两者都绕开了「有余数」这一唯一会失败的情形。
   - **修复位置。** `SessionRuntime/src/surface_service.zig::checkGeometry` 改成按同一量化基准比较（`pixels.width == cellWidth()×columns`、`pixels.height == cellHeight()×rows`）；行列仍按原值严格比较。
   - **可见性前置修复。** `SessionRuntime/src/terminal_attach.zig` 的 `Client.rpc` 在收到 error 帧时先 `reportRejection`，把 `operation / code / retry / message` 写到 stderr，再返回 `TerminalRequestRejected`。没有这一步，CLI 侧只有 Zig 错误名，服务端错误码全部丢失——这次正是靠它一次拿到 `surface.subscribe rejected: code=invalid_request retry=never`。
   - **回归。** `tests/terminal_attach.py` 的 `Host.resize` 改成上报带余数的像素尺寸（`columns*15+7` × `rows*26+11`），让套件里每一次 attach 都走这条路径。把 `checkGeometry` 还原成旧写法后该测试立即失败（`CLI output timed out: b'aster-session: surface.subscribe rejected: code=invalid_request ...'`），恢复修复后通过。

   ### 根因二：显示桥退出被判成「终端进程已退出」，掉桥的受管 Pane 再也无法分离或结束

   - **是什么。** `AsterControlDispatcher.resolveManagedTarget` 对 `session.detach` / `session.end` 使用了完整的 `AsterControlWriteGate.blocker`，其中包含 `TerminalSession.promptWriteBlocker`——那是「能不能往 surface 里键入」的判断，桥不在时返回「终端进程已退出」。于是显示桥一旦退出（桥内 `Ctrl+B q`、桥崩溃、或本次的 attach 被拒），CLI 的 detach/end 就恒返回 `write_rejected: 终端进程已退出`，而服务端进程与任务其实还在跑，与 P2.5「以服务端真实状态为准」直接冲突。
   - **为什么单测没抓到。** A08 的宿主用例都在桥正常存活的前提下调用 `TerminalSession.detachManagedTerminal()/terminateManagedTerminal()`，不经过控制协议的写门禁；控制协议的用例又没有受管 Pane。两边各测一半，缺口正好落在中间。
   - **修复位置。** `Sources/Aster/Control/AsterControlWriteGate.swift` 拆出 `policyBlocker`（只做 Allow Send Keys + 敏感会话两项权限判断）；`Sources/Aster/Control/AsterControlDispatcher.swift` 的 `resolveManagedTarget` 改用 `policyBlocker`，存活判断改问服务端（`terminal.list` 投影出来的 `live` 状态），服务端报 `exited` 才返回 `pane_not_running`。`detachManagedTerminal` 对「桥已自行退出、本地已是分离态、服务端仍在跑」按幂等成功返回，不再报 `write_rejected`。权限负例不受影响：`policyBlocker` 仍是第一道判断。

   ### 根因三：分离后视图树重建会自动重新附加，使「分离」形同无效

   - **是什么。** 修完前两项后端到端复测发现：`aster session detach` 之后 0 秒内 App 又起了一个新的 `terminal attach` 桥。`TerminalSession.makeTerminalHost` 无条件调用 `makeGhosttyTerminalView`，而分离路径刻意把 `ghosttyView` 置空，于是分离后任何一次视图树重建（布局写回、标签切换、主题刷新）都会顺手新建 surface 并拉起新桥。
   - **为什么单测没抓到。** 宿主用例只在挂载时调一次 `makeTerminalHost`，分离后不会再被 SwiftUI 重建。
   - **修复位置。** `Sources/Aster/TerminalSession.swift::makeTerminalHost`：受管终端处于 `.detached` 时只返回（必要时创建）空容器，不新建 surface；重新附加仍只走用户显式的 `reattachManagedTerminal()`。

## 6. 待确认（按默认假设推进，未阻塞）

1. **受管模式的开关形态。** 规格只要求「只向专用测试配置开放」，未规定开关放在配置文件还是环境变量。默认假设：用环境变量（`ASTER_SESSION_BINARY` + `ASTER_SESSION_STATE_DIR`）开启，不进入设置界面，也不写入 `AsterConfiguration`；P8 切默认托管时再定型。
2. **会话客户端的代码归属。** 设计草案 §3.1 说 AsterCore 承载「纯值类型和状态转换」。本实现把会话客户端协议、纯解码层与 `LocalManagedSessionClient` 一起放在 AsterCore，理由是 `aster-cli` 与 App 必须共用同一套动作语义而不复制服务端领域逻辑（§3.1 同段要求）。`Sources/Aster/Remote/` 仍只承载 App 侧编排与投影。
3. **本地后台实现的传输面。** 采用 P1 已交付的 `aster-session` 结构化 CLI 作为本机传输，而不是在 Swift 内重新实现协议分帧。`TerminalSession` 只看到「引用 + 桥命令」，未嵌入服务协议（P2.2 的原文要求）。P3 的 SSH 传输会引入长连接客户端，届时同一 `ManagedSessionClient` 接口可换实现。
4. **`detached` 是否应进入协议层状态枚举。** 客户端分离是客户端事实，服务端仍视该终端为 running。默认假设：`ManagedTerminalState`（服务端真值）不含 `detached`；客户端在 `TerminalSessionLifecycleState` 与 CLI 结果里单独表达 `detached`，本地态优先于服务端上报。
