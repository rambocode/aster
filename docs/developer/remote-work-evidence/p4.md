### 2.1 协议变更（本阶段唯一一处）

`SessionRuntime/scripts/build-protocol.py` 让错误信封新增**一个可选**顶层字段 `currentRevision`（u64），随之重新生成 `protocol/operations.schema.json`。既有操作的参数与结果定义**一个字节都没改**。

`revision_conflict` 的确切信封（客户端按它解码）：

```json
{"type":"error","requestID":"…","operation":"pane.split","scope":"session",
 "target":{"serverID":"…","serverEpoch":"…","sessionID":"…"},
 "currentRevision":2,
 "error":{"code":"revision_conflict","message":"revision_conflict","retry":"after_query"}}
```

`target` 与 `currentRevision` 只在 `revision_conflict` 时出现（该路径客户端已通过鉴权）；其余错误保持原形状。客户端两条路都实现了：直接用 `currentRevision` 重试，或忽略它改走 `session.snapshot` 取新 revision。

事件信封：

```json
{"type":"event","event":"workspace.changed","eventID":"…",
 "target":{"serverID":"…","serverEpoch":"…","sessionID":"…"},
 "sequence":7,"revision":9,"body":{ /* workspace | tab | pane | terminal */ }}
```

`sequence` 属于当前控制连接、从 1 起连续，新连接重置；`revision` 不回退。

## 5. 本轮修复的真实缺陷

### 5.1 布局 revision 跟随终端生命周期，制造假冲突并破坏 A15.2

- **是什么。** 服务端把布局 revision 与终端生命周期共用了同一个计数器（`workspace_store.zig` 的 `revision`，`terminal_service.zig` 通过 `shared_revision` 指向它）。一个受管终端被回收时，会话 revision 也 +1。
- **影响。** 两条：（1）客户端拿刚读到的 revision 提交合法布局事务，只要期间任意无关终端被回收就被判成 `revision_conflict`；（2）A15.2（继承自 A06）要求两个客户端用同一 `expectedRevision` 并发提交时**恰好一个成功**，但只要并发窗口里有终端被回收就会**两个都失败**。
- **真实复现。** 在 OrbStack 上手工执行并发 `pane split` 时两个客户端都收到 `currentRevision=2` 的冲突；随后真实验收里 `tab.close` 返回 revision 5、第二客户端快照读到 6，断言失败（`RemoteWorkP4AcceptanceTests.swift:1391`）。
- **修复位置。** `SessionRuntime/src/terminal_service.zig` 去掉 `tick()` 退出上报循环里的 `bumpRevision()`，并把 `shared_revision` 由 `?*u64` 收窄成 `?*const u64`——终端域在结构上不再可能推进布局 revision，将来的回归改不动就编译不过。`workspace_store.zig` 的注释写明 revision 是**布局** revision。
- **红/绿证据。** 修复前 `RemoteWorkP4AcceptanceTests` 的 A15 用例失败；修复后同一用例在真实远端通过，且 `tab.close` 的 revision 与第二客户端快照 revision 相等。新增覆盖：终端退出不推进 revision（snapshot revision 冻结、`terminal.exited` 仍带当前 revision 且 sequence 连续）；结构事务顺带创建终端只推进一次。

### 5.2 `RemoteWorkspaceCoordinator` 持有 `unowned AppModel`，窗口销毁后崩溃

- **是什么。** 协调器用 `unowned let model: AppModel`，注释假设「模型生命周期覆盖协调器」。但刷新、事件流回调与结构事务都是异步的，在途 `Task { @MainActor [weak self] }` 会把协调器续命到窗口销毁之后。
- **真实复现。** 真实 AppKit 宿主 + 真实远端跑第三条用例时崩溃：`Fatal error: Attempted to read an unowned reference but object 0xa34f20e00 was already destroyed`。
- **修复位置。** `Sources/Aster/Remote/RemoteWorkspaceCoordinator.swift` 改成 `private weak var model: AppModel?`，并在全部 11 处使用点加 `guard let model else { return … }`：模型不在了说明该窗口界面已经没有了，依赖模型的动作安静放弃，不让 App 崩掉。

### 5.3 事件订阅停止后的延迟任务打到已销毁的 Ghostty surface 上，测试宿主确定性崩溃

- **是什么。** `stopAllEventSubscriptions()` → `SessionEventStreamClient.stop()` 触发 `onConnectionLost(.stopped)`，协调器把它变成一个**延迟**的 `Task { @MainActor … connectionLost }`。该任务与在途 `refresh`/`handleEvent` 在夹具的窗口与 Ghostty surface 已经拆掉之后仍然排在队列里。下一条用例主线程上的 `Process.waitUntilExit()` 会**转 AppKit run loop**，这些陈旧任务于是被执行，对着已死的 surface 调 `detach/reattachManagedTerminal`，紧接着的 CoreAnimation flush 绘制已释放的 Metal renderer。
- **真实证据。** `~/Library/Logs/DiagnosticReports/aster-appkit-test-host-*.ips`：`BUG IN CLIENT OF LIBPLATFORM: os_unfair_lock is corrupt`，栈为 `_os_unfair_lock_corruption_abort ← Renderer.drawFrame ← CA::Transaction::flush_as_runloop_observer ← __CFRunLoopRun ← -[NSConcreteTask waitUntilExit]`。修复前两个真实远端用例文件一起跑 **8/8 崩溃**（exit 137），单独跑任一文件都通过——因为单独跑不会有「另一个夹具的残留任务 + 转 run loop」这个组合。
- **顺带暴露的两个生产缺陷。** （1）App 退出与窗口关闭时从不停止事件订阅，只有 `RemoteWorkspaceCoordinator.deinit` 会停，而 `AppModel.remoteStructureHandler` 会把协调器留过窗口生命周期；（2）`ProcessSessionEventLineSource` 没有 `deinit`，`readabilityHandler` 只在 `terminationHandler` 里清空。

### 5.4 已退出的终端永远不释放池槽位，会话累计 32 个终端后永久无法新建

- **是什么。** `SessionRuntime/src/terminal_pool.zig` 的 32 条记录上限把**已完全回收**的终端也算在内，记录从不释放。
- **真实复现。** 真实远端命名会话 `work2` 达到 32/32，其中 **30 条 `state=exited`、只有 2 条在跑**，`pane split` 一律返回 `resource_limit`。长期运行的共享工作区在累计创建 32 个终端后永久无法再新建终端。
- **修复位置。** `SessionRuntime/src/terminal_pool.zig` + `terminal_service.zig`，见 §5.4.1。

### 5.4.1 修复设计、接线与红/绿

**设计取舍。** 32 这个上限存在的目的是**限制活的 PTY、VT 和子进程**，不是限制一个长期工作区的历史长度。所以：一条记录只要「子进程已回收 + PTY master 已关 + 没有未完成的清理」（`reclaimed()`），它就只剩簿记价值，可以让出槽位；而 `running` / `terminating` 的终端**永远不会**被驱逐，满池且无可回收记录时仍然如实返回 `resource_limit`——为了给新终端腾地方去杀掉用户正在跑的东西是不可接受的。驱逐按**最旧优先**，让活下来的摘要是最近的那些。

**为什么要保留「退休摘要」而不是直接删记录。** 一个客户端可能正好在终端退出时有一条在途的 `terminal.terminate` 或 `request.status`；记录直接消失会让它读到「终端不存在」而不是真实退出码。所以让出槽位的记录留下一份 `Retired`（只有 ID、cwd 文本、退出状态、是否不可用，**不持有 Session**，因此绝不可能被报成 running），放进一个**有界** FIFO：`recent_exit_capacity = 8`。有界是必须的——共享工作区会连续跑几周，无界退出流水账就是这个泄漏本身换了个名字。

**接线的四处（缺一处就还是错的）。**

| 位置 | 改动 | 不改会怎样 |
| --- | --- | --- |
| `Pool.validateLaunch` | 满池时先 `reclaimSlot()` 再决定是否拒绝 | 缺陷本体：32 个死记录永久占位 |
| `Service.terminal.list` / `terminal.get` / 在途 terminate 完成 / `request.status` 的 invalidated 判定 | 一律先查 `find`，再查 `findRetired` | 终端会在两次轮询之间「凭空消失」，或已提交的操作被当成仍然有效 |
| `Service.takeExitEvent` | 队列里的退出事件回退到退休摘要；摘要也过期就跳过该事件，而不是 `unreachable` | 槽位复用后原来的 `orelse unreachable` 直接 panic |
| 「已上报退出」闩锁 | 从**按槽位下标的位掩码** `reported_exits & (1 << slot)` 改成**记录上的** `entry.exit_reported` | 槽位现在会复用，下标掩码会把新终端的退出事件误判成「已上报」而永久吞掉 |

### 5.5.1 显示桥租约不释放：根因与红/绿

**症状（红）。** §3.5 的用例在 (e3) 失败：分离后本机桥确实退出、远端进程也确实没动，但重新附加建起来的新桥在屏幕上写着
`aster-session: terminal.attach rejected: code=lease_busy retry=never`，marker 永远不出现。远端 `ps` 显示旧的 `terminal attach` 进程还活着（PID 2348，`ppid=7`，已被 init 收养）。失败日志 `.build/remote-work-evidence/p4-bridge-e2e.log`、`p4-bridge-e2e-run.log`。

**根因 1：桥挂在共享的 ControlMaster 上，本机进程死了远端会话通道不关。** Aster 的私有 SSH 配置对所有连接开 `ControlMaster auto` + `ControlPersist 60`（`RemoteSSHConfigurationManager.configurationText`）。短命控制命令靠它省掉握手，这是对的；但显示桥是一条**长命流**，它的会话通道挂在后台 master 进程上。本机桥被杀死时 master 并不立刻关闭该通道，远端 `terminal attach` 继续跑，并且每 5 秒发一次 `health.check` + 空输入续租（`terminal_attach.zig` 的心跳），所以 15 秒的不活动过期永远不会触发——它不是「连着但不写」，它是**真的还连着**。旧桥要等 master 自己因 `ControlPersist 60` 退出才被拖走。

**根因 2：分离从不给桥一个自己退出的机会。** `terminal attach` 正常退出时会 `defer` 一次 `terminal.release`，租约立刻还回去；而 `finishManagedDetach` 直接 `destroySurface()` 杀本机进程，走的是「传输断开」路径，服务端必须等连接真的断掉才回收 attachment 与租约。即便修掉根因 1（断开后约 2 秒回收），紧接着的重新附加仍然会撞上这 2 秒窗口。

**红/绿证据（真实 OrbStack 远端，同一个终端 ID，三组对照）：** `.build/remote-work-evidence/p4-bridge-lease-rootcause.log`，runID `p4rc-20260909-215305`，终端 `89e5477a-8685-4314-86b4-fa74f16eca35`。每组都先用一条普通控制命令建立 ControlMaster，完全复现产品运行时状态；退出时刻按远端进程 PID 逐秒探测。

| 组 | 桥的结束方式 | 远端 attach 退出 | 结束本机桥后**立刻**重新附加 |
| --- | --- | --- | --- |
| `muxed`（修复前的产品形态） | `kill -KILL` | **60 秒**（= `ControlPersist 60`） | **被 `lease_busy retry=never` 拒绝 ✘** |
| `dedicated`（修复 A：桥加 `-o ControlPath=none`） | `kill -KILL` | 2 秒（单独测量值） | 未被租约拒绝 ✔ |
| `escape`（修复 A + B：先写分离转义再结束） | 写入 `Ctrl-B q` | 1 秒（单独测量值） | 未被租约拒绝 ✔ |

**修复 A（`Sources/AsterCore/RemoteManagedSessionClient.swift`）：** `RemoteSessionTransport.sshArguments` 增加 `multiplexed` 形参；`bridgeArguments` 与 `eventSubscribeInvocation` 传 `false`，即在命令行补 `-o ControlPath=none`。必须是 `ControlPath=none` 而不是 `ControlMaster=no`——后者仍然会去连已存在的 control socket。短命控制命令保持复用不变。回归单测 `remoteManagedSessionClientKeepsLongLivedStreamsOffTheControlMaster`。

**修复 B（`Sources/Aster/TerminalSession.swift`）：** 新增 `shutDownManagedBridge(_:immediately:)`。分离时先用 `sendProtocolBytes([0x02, 0x71])` 向桥写 `terminal attach` 自己的分离转义（Ctrl-B q），让它走正常退出路径把租约还回去，最多等 2 秒再 `destroySurface()`；桥没在跑、写入失败、或 App 正在退出（`immediately`）时保持原来的直接强拆。A08 的分离/保活/重新附加语义不变（`managedTerminal` 系列用例全绿）。

## 7. 待确认（按默认假设推进，未阻塞）

1. **注册表的物理形态。** 草案只说「每个命名会话运行独立后台服务」，没有定义注册表存在哪里。**默认假设**：注册表就是那个私有 state parent 目录，每个命名会话是它下面的一个子目录，稳定 sessionID 取自该会话已有的持久 `identity.bin`。`registry` scope 请求到达某个会话服务时，该服务用自己所在的 parent 目录来服务它；没有服务在跑时走 CLI 直接读目录。没有committed `identity.bin` 的目录不算会话，`session.list` 跳过（没有稳定 sessionID 可报）。
2. **会话不能通过注册表停止自己。** 一个服务无法在处理请求的过程中驱动自己的停止握手，因此 `session.stop` 指向服务自身时返回 `invalid_request`，自停走 session scope 的 `server.stop`。它仍然能用自己的身份回答关于自己的注册表查询。
3. **服务内的 `session.create` 不 fork 自己。** fork 一个活服务会继承它的信号管道（`session_bridge_signals_start` 返回 EBUSY）与 PTY 描述符并留下僵尸，所以服务改为运行已安装二进制自己的 `server start`（它会 fork、detach 再退出）。CLI 路径仍用直接的进程内 fork。
4. **错误信封的 `currentRevision` 放在顶层而不是 `error` 里。** 只在 `revision_conflict` 时随 `target` 一起出现（该路径客户端已通过鉴权）。客户端两条路都实现了：直接用它重试，或忽略它改走 `session.snapshot`。**默认假设**：这是纯增量的可选字段，不构成协议主版本变更。
5. **关闭类事件没有独立的「删除」变体。** `events.schema.json` 没有 removal 事件，所以 `tab.close` / `pane.close` 发受影响的父节点（`workspace.changed` / `tab.changed`）带新内容；被关闭的工作区报成 `workspace.changed` 且 `"tabs": []`。
6. **`cwd_unavailable` 是未在 `operations.json` 里声明的错误码。** `workspace.create` / `tab.create` / `pane.split` 的 `errors` 列表是空的，但「远端目录须在执行机器校验」是硬要求，所以按未声明（仍然 schema 合法）的错误码返回，没有改那三处声明。
7. **事件正文只当变更信号。** 权威结构仍然是快照：顺序正确与序号缺口都触发重新取快照，客户端不在本地拼装新树。未知事件类型推进连接序号（它确实消耗了一个），但报成需要重同步，绝不当成已应用的业务变更。
8. **事件订阅没有自动重连。** 流结束报 `connectionLost`，重新订阅发生在下一次 `ensureWorkspace`。加退避重连会和 `MachineConnectionSupervisor` 的职责重复。
9. **订阅入口的首行叫 `subscribed` 而不是 `hello`。** 线上的 `hello` 帧不带 revision，用不同的名字避免歧义；解码器两种都接受。基线 revision 由订阅进程发一次空 `health.check` 取得，握手行之前到达的事件被有界缓冲（上限 256）后补发，不丢弃。
10. **订阅进程的保活。** reactor 会丢弃 30 秒无流量的控制连接。没有改服务端行为，而是让订阅进程每 10 秒发一次 `health.check` 并丢弃回复。租约、订阅与终端语义都不受影响，慢消费者背压仍走既有规则。
11. **机器侧栏的挂载方式。** `WorkspacePanelRole` 是 AsterCore 里的枚举，本阶段没有改它。机器分区是插进现有 `sidebar` 面板列栈里的一个可折叠分区（在 TABS 之上），复用 `SidebarGroupHeaderView` 与折叠偏好（键 `__machines__`）。**因此机器分区只在标签栏布局为「竖直（侧栏）」时出现**；顶/底标签栏布局下只有主菜单的「添加机器…」入口。
12. **机器配置存成单个 `machines.json`** 而不是每机器一文件，默认 `~/Library/Application Support/Aster/machines.json`（目录 0700、文件 0600），路径可注入。
13. **`machine.*` 写方法只走 IPC 全局写开关**（`allowSendKeys`），不走 Pane 级敏感会话/可写性判断——它们不向任何 PTY 写字节。
14. **受管协调器注册表不抛错也不返回 nil。** 没有机器引用、未知机器、未配置远端运行时，全部回落到 `ManagedTerminalCoordinator.shared`（实时读取，测试替换 `shared` 仍然有效）。代价是配错的远端 Pane 会静默地去和本机服务对账并报「终端不存在」，而不是给出按机器区分的错误。这样取舍是为了不破坏 Local 受管终端的分离/保活（A08）。
15. **`terminal.updated`** 在 `events.schema.json` 里有声明，但运行时目前不发送；只有 `terminal.created` 与 `terminal.exited` 会发。
